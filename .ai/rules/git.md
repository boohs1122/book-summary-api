# Git 규칙

공개 저장소이므로 커밋 히스토리도 코드와 함께 읽힌다.
나중에 고칠 수 없는 영역이라 처음부터 지킨다.

## 브랜치

| 항목 | 규칙 |
|---|---|
| 기본 브랜치 | `main` |
| 기능 브랜치 | `feature/{기능명}` |
| 수정 브랜치 | `fix/{대상}` |

- 기능명은 영문 소문자와 하이픈으로 쓴다. 예: `feature/book-list`, `fix/ocr-threshold`

## PR

기능 단위 기록을 남기기 위해 PR을 쓴다. 혼자 작업하므로 리뷰 절차는 두지 않는다.

| 변경 | 방식 |
|---|---|
| 기능 구현 (`feature/*`) | PR로 병합 |
| 버그 수정 (`fix/*`) | 원인 설명이 필요하면 PR, 단순 수정은 `main`에 직접 커밋 |
| 문서·설정·의존성 (`docs`, `chore`) | `main`에 직접 커밋 |

- PR 제목은 커밋 제목 형식(`{타입}({스코프}): {요약}`)을 따른다
- 본문은 `.github/PULL_REQUEST_TEMPLATE.md`를 따른다
- 화면이 바뀌면 스크린샷이나 GIF를 첨부한다
- 병합은 "Create a merge commit"으로 한다. 개별 커밋과 PR 경계를 모두 기록에 남긴다
- 병합한 브랜치는 삭제한다

## 커밋 메시지

### 형식

```
{타입}({스코프}): {요약}

{본문 — 필요한 경우에만}
```

### 제목

- 50자 이내. 마침표를 찍지 않는다
- 한국어로 쓴다
- 무엇을 했는지 서술한다. "~함", "~추가" 형태로 끝낸다
- 타입과 스코프는 영문 소문자
- 이모지를 붙이지 않는다. 도구·터미널 호환성 문제가 있고 업무 환경의
  일반적인 관례와 다르다

### 타입

| 타입 | 대상 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 변경 |
| `chore` | 빌드, 설정, 의존성 |
| `style` | 포맷팅, 세미콜론 등 동작과 무관한 변경 |
| `perf` | 동작은 같고 성능만 개선 |
| `security` | 인증, 키 관리, 권한 관련 변경 |

`wip` 타입은 두지 않는다. 한 커밋이 한 가지 완결된 일을 담는다는 원칙과
충돌하며, 공개를 전제로 한 히스토리에 미완성 커밋을 남기지 않는다.

### 스코프

기능 폴더명을 사용한다. 전역 변경이면 생략한다.

| 저장소 | 스코프 |
|---|---|
| 앱 | `library`, `capture`, `summary`, `quiz`, `core` |
| 서버 | `book`, `document`, `summary`, `quiz`, `llm`, `common` |

### 본문

제목만으로 충분하면 쓰지 않는다. 아래에 해당하면 쓴다.

- **왜** 그렇게 했는지 설명이 필요할 때
- 선택하지 않은 대안이 있을 때
- 다른 저장소나 문서와 연결되는 변경일 때

무엇을 바꿨는지는 diff가 말해준다. 본문에는 diff에 드러나지 않는 것을 적는다.

- 본문은 `- ` 목록으로 쓴다. 한 줄에 한 가지만 적는다
- 문장은 "~함", "~둠"처럼 명사형으로 끝낸다

```
feat(quiz): 퀴즈 생성 대기를 버튼 내 처리로 구현

- 별도 대기 화면으로 전환하면 요약을 읽을 수 없어 S8에서 버튼 내 스피너로 표시함
- 생성 시간이 10초를 넘기면 방식 재검토
```

### 예시

```
✓ feat(capture): ML Kit OCR 연동 및 페이지 순서 병합 구현
✓ fix(summary): 폴링 중 앱 복귀 시 jobId 유실되는 문제 수정
✓ refactor(llm): GeminiClient를 LlmClient 인터페이스 뒤로 분리
✓ docs: 책·회차 2단계 구조를 화면 흐름에 반영
✓ chore: Riverpod 및 json_serializable 의존성 추가

✗ 작업 완료
✗ 수정
✗ feat: 여러 기능 추가함
✗ update BookListScreen.dart
```

## 커밋 단위

한 커밋은 한 가지 일만 담는다. 되돌릴 때 원하는 것만 되돌릴 수 있어야 한다.

| 상황 | 처리 |
|---|---|
| 기능 구현 + 오타 수정 | 커밋 분리 |
| 기능 구현 + 그에 필요한 의존성 추가 | 같은 커밋 가능 |
| 여러 화면을 동시에 만짐 | 화면별로 분리 |
| 포맷팅이 대량 발생 | `style`로 따로 분리 |

작업 도중 커밋 단위가 섞였다면 `git add -p`로 나눠 담는다.

## 저장소 간 동기화

API 스펙 변경은 앱과 서버 두 저장소에 걸친다. 양쪽 커밋 메시지에 같은 요약을
남겨 나중에 짝을 찾을 수 있게 한다. 본문에 상대 저장소의 변경 내용을 한 줄 적는다.

## 커밋 절차

AI가 커밋을 만들 때 따르는 순서다.

1. `git status`와 `git diff HEAD`로 변경 내용을 확인한다
2. 변경에 성격이 다른 작업이 섞여 있으면 **커밋 분리를 먼저 제안한다**
3. 사전 검사를 실행한다 (아래 절 참고)
4. `git log --oneline -10`으로 기존 메시지 스타일을 확인한다
5. 이 문서의 형식에 맞춰 메시지를 작성한다
6. **메시지를 사용자에게 제시하고 승인을 받는다**
7. 승인 후에만 스테이징하고 커밋한다

커밋과 푸시는 사용자 확인을 거친다. 임의로 실행하지 않는다.

## 사전 검사

커밋 전에 포맷과 정적 분석을 통과하는지 확인한다.

| 저장소 | 명령 |
|---|---|
| 앱 | `dart format --set-exit-if-changed lib test` · `flutter analyze` |
| 서버 | `./gradlew ktlintCheck build` |

앱 포맷 대상은 `lib`·`test`로 한정한다. `.`을 쓰면 iOS 빌드 후 `build/`에
받아 둔 패키지 소스까지 검사해 실패한다.

검사에 실패하면 커밋하지 않고 사용자에게 실패 내용을 보고한다. 건너뛰어야
할 사정이 있으면 사용자가 판단한다. AI가 임의로 생략하지 않는다.

공개를 전제로 한 히스토리이므로 빌드가 깨진 커밋을 남기지 않는다.
나중에 고칠 수 없는 영역이다.

## 공동 저자 표기

커밋 메시지와 PR 본문에 `Co-Authored-By` 푸터나 "Generated with ..." 같은
AI 작업 표기를 넣지 않는다. 도구가 기본으로 붙이는 경우에도 제거한다.
AI 활용 사실은 README의 개발 방식 항목에 기술한다. 표기를 생략하는 것이지
숨기는 것이 아니다.

## 커밋하지 않는 것

- `.env`, 인증 키, 토큰이 담긴 파일
- `build/`, `.dart_tool/`, `.gradle/`, `local.properties`
- IDE 설정 중 개인 환경에 종속된 것
- 대용량 바이너리

커밋 전 `git status`에 의도하지 않은 파일이 있는지 확인한다.

## 브랜치 정리

원격에서 삭제된 브랜치를 로컬에서 지울 때 주의한다.

```bash
git fetch --prune
git branch -vv | grep '\[gone\]'    # -v 가 아니라 -vv 여야 추적 정보가 나온다
```

`git branch -v`에는 upstream 정보가 없어 `[gone]`이 표시되지 않는다.
이를 쓰는 자동화 도구는 항상 빈 결과를 낸다.

삭제는 `git branch -d`를 쓴다. `-D`는 머지되지 않은 브랜치도 지우므로
확인 없이 사용하지 않는다. 워크트리가 연결된 브랜치는 워크트리를 먼저
정리하되, 저장되지 않은 변경이 있는지 확인한 뒤 진행한다.
