# 아키텍처 규칙

## 구조

레이어드 구조를 기본으로 하고, LLM만 포트/어댑터로 분리한다.

```
src/main/kotlin/com/boohs/booksummary/
├── controller/         HTTP 경계. 요청 검증과 응답 변환만
├── service/            유스케이스. 트랜잭션 경계
├── repository/         데이터 접근
├── domain/             엔티티
├── dto/                요청·응답 모델
├── llm/
│   ├── LlmClient.kt            인터페이스 (포트)
│   ├── GeminiClient.kt         구현 (어댑터)
│   ├── prompt/                 프롬프트 템플릿
│   └── validator/              응답 스키마 검증
├── config/             설정
└── common/             예외, 에러 코드, 공통 응답
```

## LLM만 추상화하는 이유

무료 티어에서 시작해 한도나 품질 문제로 교체할 가능성이 높다. 테스트에서도
실제 호출 대신 고정 응답을 끼워넣어야 한다. 교체 가능성이 실재하는 지점만
인터페이스로 감싸고, 나머지는 추상화하지 않는다.

`service`는 `LlmClient` 인터페이스만 알고 구현체를 모른다.

## 계층 규칙

- `controller`는 비즈니스 로직을 갖지 않는다. 검증과 위임만 한다
- `service`는 `dto`를 반환하지 않고 `domain`을 다룬다. 변환은 `controller`에서 한다
- `repository`는 `service`를 통해서만 호출된다
- 엔티티를 그대로 응답에 노출하지 않는다

## 비동기 작업

요약과 퀴즈 생성은 LLM 호출이 포함되어 즉시 끝나지 않는다.
요청 즉시 `Job` 레코드를 만들고 `202 Accepted`로 `jobId`를 반환한 뒤,
별도 스레드에서 생성을 진행하고 완료 시 `Job` 상태를 갱신한다.

작업 취소 엔드포인트는 두지 않는다. 이미 시작된 LLM 호출은 중단해도 비용이
절약되지 않고, 결과를 남기는 편이 재시도보다 낫다.

## 응답 검증

LLM 응답은 구조화 출력으로 받되 항상 검증한다.

- 요약: 필수 필드, 핵심 항목 수
- 퀴즈: 문항 수, 선택지 4개, `answerIndex` 범위

검증 실패 시 1회 재요청하고, 재차 실패하면 `LLM_INVALID_RESPONSE`로 작업을 종료한다.
